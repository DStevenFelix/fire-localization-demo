4. 业务流程与真实信息边界
正常初始 → 地图起火 → SocialNet 舆情监测 → 火情定位 Top3 → 调度 Agent 收到候选 → 无人机侦查/返回结果 → 调度 Agent 派遣消防车 → 车辆定位/路线展示 → 灭火反馈 → 处置完成/恢复待命。

核心区分：仿真世界/地图展示层可以知道真实火点 Ground Truth，但舆情、定位、调度 Agent 和实体设备不能经前端接口直接获得它。Agent 只能看到自身有权获得的帖子、候选、侦查反馈和任务结果；用户在地图看见火点不构成 Agent 获知火点。演示模式不得把 Ground Truth 隐蔽塞入最后航点、方案目标、假侦查结果；若做专门的“理想答案对照”展示，必须与真实 Agent 输入通道物理/逻辑隔离并显式标识。

对一个火情事件，状态和任务日志应按真实事件转换，不因暂停页面、改变视角、接收视频帧而自动推导任务成功。恢复/全局重置必须遵守现有 Session 和应急状态机语义，真实联动模式绝不把“前端重置”错误解释为“命令硬件复位”。

5.1 已确认的几何参数

仅当设备上报坐标已定义为“沙盘西南原点、米单位、X 东 Y 北、无旋转”的轴对齐局部物理坐标，才能使用：
localX = physicalEastMeters  / 5 × 30
localY = physicalNorthMeters / 4 × 25
cityX  = 30 + localX
cityY  = 25 + localY
例如真实沙盘中心 (2.5m, 2.0m) → LOCAL(15, 12.5) → CITY(45, 37.5)。物理每米对应逻辑 X=6 单位、Y=6.25 单位。这不是任意设备消息都可直接套用的通用公式；需要后端明确其坐标单位、原点、轴向、旋转、时间戳和精度后使用标定参数转换。最终渲染继续调用现有 sceneToPixel / 地图 ViewBox 转换，不能私自新建一份不一致的像素比例逻辑。

标定接口至少表达 sourceCoordinateSystem、`origin`、`axisDirection`、`physicalBounds`、`mapBounds`、`rotation/transform`、`version`；若后端提供 GPS/相机像素/机器人自身坐标，需明确可验证的映射及坐标基准，不允许猜算。转换要处理越界、非有限值、校准未就绪以及前后向往返测试。物理 5:4、原图约 1313:1050、逻辑 30:25 的比例各不相同，绝不能拉伸现有地图来强行匹配。
5.2 消防车：前端统一四辆展示（替代旧“三车可见”语义）
- 设备清单固定四辆：消防车 1、2、3、4。 用户图中消防车1～4的红字位置代表物理沙盘内的部署/进入参考区域，精确的真实硬件停车点尚未由定位消息确认；不能据文字/图片估算出具有物理精度的四个坐标。前端必须有可配置的 displayId ↔ deviceId ↔ legacyVehicleId? 映射，避免后端消息使用其他编号时错车。
- 前端开机但未收到设备定位时：在真实核心区外围邻近的道路/待命区以灰色或半透明虚拟待命标记显示 4 辆（位置可配置，不应阻断既有交通路网），标记“未收到真实定位”，不得当作真实硬件在线/停放位置。
- 首个有效真实定位到达时：设备展示进入“真实定位接管”，立即定位到经标定的真实位置（可短暂视觉过渡，但不能伪造从虚拟点行驶过来的历史轨迹）；之后持续按带时间戳的真实定位更新，并可对相邻有效采样做有界平滑。设备停止、定位过期、断线时冻结最后有效位置并显示质量/失联状态。
- 真正调度后由外部调度 Agent 提供路线、目标、任务状态及位置反馈。规划路径与实际轨迹分图层显示；不能根据前端规划点自行冒充实际位移。实际物理区域与虚拟外围移动的切换方式以设备输入为准。
- 主地图上仅保留四辆消防车的统一可见实例。原 VehicleLayer/`TrafficSimulation` 的三车默认渲染、场景快照、应急状态需在前端做一致适配：可复用底层交通运动，也可将旧三车变为内部模拟源，但不得和四设备实体同时叠加或同时计数。四车 Mock 各自有初始待命、首次定位接管、状态更新、路线与实际移动，不能第四辆只变为 CSS 装饰。普通交通车辆依然正常运行，原有 3 泊位的基础数据原样保留。
5.3 无人机：两架、站点固定、飞行由消息决定
